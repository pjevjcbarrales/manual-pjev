04.2.2

Validación de Depósitos y Recaudación

Bandeja de operaciones financieras de Tesorería donde se consultan los ingresos devengados pendientes de cobro, se precarga la información básica de la solicitud institucional y se valida el comprobante bancario oficial para formalizar el momento contable y presupuestario Recaudado.

Modo B — Bandeja Transaccional de Tesorería Tipo: Análisis Funcional (DOC-08)
📌 Segregación de Funciones y Principio KISS

Este módulo divide arquitectónicamente el ciclo de vida del ingreso: el área de Programación y Presupuesto devenga la solicitud en 04.2.1 con sus archivos de firmas colegiadas y desglose de capítulos, y el área de Tesorería y Caja valida el depósito bancario en este módulo cuando el dinero se acredita efectivamente en la cuenta.

Principio KISS con Precarga: El cajero o tesorero no vuelve a teclear importes, órganos ni conceptos; al seleccionar una partida devengada de la bandeja, el sistema precarga toda la información y el usuario únicamente captura los datos del depósito (Banco, Cuenta, Fecha valor, Folio de autorización BBVA/Banorte y PDF del comprobante bancario).

1 Descripción General

El módulo 04.2.2 Validación de Depósitos y Recaudación constituye la ventanilla operativa de Caja y Tesorería del Poder Judicial del Estado de Veracruz para el reconocimiento en firme de los flujos de efectivo percibidos.

Opera como una Bandeja de Entrada Dinámica que lista todos los trámites de ingreso que han alcanzado el estado DEVENGADO (o que presentan saldos parciales por cobrar). Cuando el operador bancario coteja el estado de cuenta electrónico (BBVA Net Cash, Banorte en Línea, etc.) y confirma el abono bancario, selecciona la operación en la bandeja. El sistema precarga automáticamente los datos de la orden original y habilita un formulario simplificado donde se asientan las referencias bancarias y se carga la ficha probatoria digital, liquidando la cuenta por cobrar y detonando la póliza del momento Recaudado (CONAC 8.1.5).

2 Objetivo y Alcance

Objetivo: Proveer a Tesorería de una interfaz ergonómica e intuitiva para acreditar depósitos bancarios asociados a órdenes devengadas, garantizando el cuadre exacto entre el extracto bancario, el recibo institucional y los momentos contables CONAC.

Dentro del Alcance Fuera del Alcance
  • Bandeja de ingresos pendientes de cobro con filtros por banco, ejercicio y estatus.
  • Precarga automática de datos maestros (Folio, Orden, Trámite SEFIPLAN, Órganos e Importe).
  • Validación y selección de la Cuenta Bancaria Recaudadora (catálogo 04.1.4).
  • Captura obligatoria de Folio de Autorización Bancaria y Fecha Valor del depósito.
  • Carga del comprobante digital oficial bancario (PDF de BBVA Net Cash / Banorte).
  • Soporte de recaudación total o abonos parciales sucesivos.
  • Generación automática de la póliza de Recaudado (Bancos 1.1.1.2 vs CxC 1.1.2.2).
  • Modificación de partidas presupuestales de la solicitud (deben realizarse en 04.2.1 si no está devengado).
  • Dispersión de transferencias de gasto o nómina (corresponde a Pagos 06.2).
  • Cédula de auditoría mensual de conciliación (se realiza en 04.3.1).

6 Procedimientos Almacenados (Stored Procedures)

Gobernanza transaccional en PostgreSQL bajo convención SECURITY DEFINER, SET search_path y respuesta estándar JSONB.

6.1. Bandeja de Pendientes (ingresos.fn_leer_pendientes_recaudar)

CREATE OR REPLACE FUNCTION ingresos.fn_leer_pendientes_recaudar(
    p_usuario VARCHAR,
    p_ejercicio SMALLINT DEFAULT 2026,
    p_banco_filtro VARCHAR DEFAULT NULL,
    p_texto_busqueda VARCHAR DEFAULT NULL
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ingresos, contabilidad, config, public
AS $$
DECLARE
    v_data JSONB;
BEGIN
    SELECT jsonb_agg(
        jsonb_build_object(
            'ingreso_id', ie.ingreso_id,
            'folio_interno', ie.folio_interno,
            'fecha_elaboracion', ie.fecha_elaboracion,
            'fecha_esperada', ie.fecha_esperada,
            'denominacion_concepto', ie.denominacion_concepto,
            'oficio_soporte', ie.oficio_soporte,
            'tramite_sefiplan', ie.tramite_sefiplan,
            'clave_orden', ie.clave_orden,
            'instruccion_abono_cuenta', ie.instruccion_abono_cuenta,
            'origen_depositante', ie.origen_depositante,
            'importe_total', ie.importe_total,
            'saldo_pendiente', ie.saldo_pendiente,
            'estatus', ie.estatus,
            'organos_resumen', (
                SELECT jsonb_agg(DISTINCT id.organo_beneficiario)
                FROM ingresos.ingresos_distribucion id
                WHERE id.ingreso_id = ie.ingreso_id
            )
        ) ORDER BY ie.fecha_esperada ASC, ie.ingreso_id DESC
    )
    INTO v_data
    FROM ingresos.ingresos_encabezado ie
    WHERE ie.ejercicio_fiscal = p_ejercicio
      AND ie.estatus IN ('DEVENGADO', 'PARCIAL')
      AND (p_banco_filtro IS NULL OR ie.instruccion_abono_cuenta LIKE '%' || p_banco_filtro || '%')
      AND (p_texto_busqueda IS NULL OR (
          ie.folio_interno ILIKE '%' || p_texto_busqueda || '%' OR
          ie.oficio_soporte ILIKE '%' || p_texto_busqueda || '%' OR
          ie.denominacion_concepto ILIKE '%' || p_texto_busqueda || '%'
      ));

    RETURN jsonb_build_object(
        'error', 0,
        'mensaje', 'Ingresos pendientes de recaudar obtenidos exitosamente.',
        'data', COALESCE(v_data, '[]'::jsonb)
    );
EXCEPTION WHEN OTHERS THEN
    RETURN jsonb_build_object('error', -2, 'mensaje', 'Error en consulta de bandeja: ' || SQLERRM, 'data', NULL);
END;
$$;

6.2. Aplicación de Depósito (ingresos.fn_aplicar_deposito_recaudacion)

CREATE OR REPLACE FUNCTION ingresos.fn_aplicar_deposito_recaudacion(
    p_usuario VARCHAR,
    p_payload JSONB
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ingresos, contabilidad, config, public
AS $$
DECLARE
    v_ingreso_id BIGINT;
    v_cuenta_id BIGINT;
    v_monto_deposito DECIMAL(18,2);
    v_saldo_actual DECIMAL(18,2);
    v_nuevo_saldo DECIMAL(18,2);
    v_nuevo_estado VARCHAR(30);
    v_deposito_id BIGINT;
    v_folio_banco VARCHAR(60);
    v_poliza_id BIGINT;
BEGIN
    v_ingreso_id    := (p_payload->>'ingreso_id')::BIGINT;
    v_cuenta_id     := (p_payload->>'cuenta_bancaria_id')::BIGINT;
    v_monto_deposito:= (p_payload->>'importe_depositado')::DECIMAL(18,2);
    v_folio_banco   := TRIM(p_payload->>'folio_autorizacion_banco');

    -- Validaciones de Integridad Financiera
    IF v_monto_deposito <= 0 THEN
        RETURN jsonb_build_object('error', -1, 'mensaje', 'El importe depositado debe ser estrictamente mayor a $0.00.');
    END IF;

    SELECT saldo_pendiente, estatus INTO v_saldo_actual, v_nuevo_estado
    FROM ingresos.ingresos_encabezado
    WHERE ingreso_id = v_ingreso_id;

    IF v_saldo_actual IS NULL THEN
        RETURN jsonb_build_object('error', -1, 'mensaje', 'El trámite de ingreso especificado no existe.');
    END IF;

    IF v_monto_deposito > v_saldo_actual THEN
        RETURN jsonb_build_object('error', -1, 'mensaje', 'El importe depositado ($' || v_monto_deposito || ') excede el saldo pendiente ($' || v_saldo_actual || ').');
    END IF;

    -- Verificar que el folio de autorización bancaria no exista duplicado en esa cuenta
    IF EXISTS (
        SELECT 1 FROM ingresos.ingresos_depositos
        WHERE cuenta_bancaria_id = v_cuenta_id
          AND folio_autorizacion_banco = v_folio_banco
          AND estatus_registro = 1
    ) THEN
        RETURN jsonb_build_object('error', -1, 'mensaje', 'El folio bancario ' || v_folio_banco || ' ya fue registrado previamente para esta cuenta.');
    END IF;

    -- Insertar registro del depósito bancario comprobado
    INSERT INTO ingresos.ingresos_depositos (
        f_ingreso_id, cuenta_bancaria_id, institucion_bancaria, numero_cuenta,
        folio_autorizacion_banco, fecha_deposito, importe_depositado,
        archivo_comprobante_id, nombre_archivo_comprobante, observaciones,
        estatus_registro, usuario_c, fecha_c
    ) VALUES (
        v_ingreso_id, v_cuenta_id, TRIM(p_payload->>'institucion_bancaria'),
        TRIM(p_payload->>'numero_cuenta'), v_folio_banco,
        (p_payload->>'fecha_deposito')::DATE, v_monto_deposito,
        (p_payload->>'archivo_comprobante_id')::BIGINT,
        TRIM(p_payload->>'nombre_archivo_comprobante'),
        p_payload->>'observaciones', 1, p_usuario, CURRENT_TIMESTAMP
    ) RETURNING deposito_id INTO v_deposito_id;

    -- Actualizar saldos y estado del encabezado
    v_nuevo_saldo := v_saldo_actual - v_monto_deposito;
    IF v_nuevo_saldo = 0 THEN
        v_nuevo_estado := 'RECAUDADO';
    ELSE
        v_nuevo_estado := 'PARCIAL';
    END IF;

    UPDATE ingresos.ingresos_encabezado SET
        saldo_pendiente = v_nuevo_saldo,
        estatus         = v_nuevo_estado
    WHERE ingreso_id = v_ingreso_id;

    -- Bitácora de Workflow
    INSERT INTO ingresos.ingreso_historial (
        f_ingreso_id, estado_anterior, estado_nuevo, accion_realizada,
        observaciones, fecha_envio, usuario_accion, fecha_accion
    ) VALUES (
        v_ingreso_id, 'DEVENGADO', v_nuevo_estado, 'VALIDAR_DEPOSITO',
        'Depósito bancario validado. Folio ' || v_folio_banco || ' por $' || v_monto_deposito,
        (p_payload->>'fecha_deposito')::DATE, p_usuario, clock_timestamp()
    );

    RETURN jsonb_build_object(
        'error', 0,
        'mensaje', 'Depósito bancario validado y formalizado exitosamente en estado ' || v_nuevo_estado,
        'data', jsonb_build_object(
            'deposito_id', v_deposito_id,
            'nuevo_saldo_pendiente', v_nuevo_saldo,
            'nuevo_estado', v_nuevo_estado
        )
    );
EXCEPTION WHEN OTHERS THEN
    RETURN jsonb_build_object('error', -2, 'mensaje', 'Error al validar depósito bancario: ' || SQLERRM, 'data', NULL);
END;
$$;

// NestJS Controller: ValidacionDepositosController
@ApiTags('04.2.2 Validación de Depósitos y Recaudación')
@Controller('api/v1/ingresos/depositos')
@UseGuards(JwtAuthGuard, RolesGuard)
export class ValidacionDepositosController {
  constructor(private readonly service: ValidacionDepositosService) {}

  @Get('pendientes')
  @ApiOperation({ summary: 'Listar operaciones devengadas pendientes de recaudar' })
  async listarPendientes(
    @Query('ejercicio') ejercicio: number = 2026,
    @Query('banco') banco?: string,
    @Query('q') query?: string,
    @CurrentUser() user: UserSession
  ) {
    return this.service.obtenerPendientes(user.username, ejercicio, banco, query);
  }

  @Get(':ingresoId/precarga')
  @ApiOperation({ summary: 'Obtener información básica precargada para modal de depósito' })
  async precargar(
    @Param('ingresoId', ParseIntPipe) ingresoId: number,
    @CurrentUser() user: UserSession
  ) {
    return this.service.obtenerDatosPrecarga(user.username, ingresoId);
  }

  @Post('aplicar')
  @ApiOperation({ summary: 'Validar comprobante bancario y formalizar la recaudación' })
  async aplicarDeposito(
    @Body() dto: AplicarDepositoDto,
    @CurrentUser() user: UserSession
  ) {
    return this.service.aplicarDepositoRecaudacion(user.username, dto);
  }
}
8 Reglas de Negocio Institucionales
CódigoReglaDescripción Operativa
RN-DEP-01 Requisito Previo de Devengo Únicamente pueden ser objeto de validación y depósito bancario aquellas operaciones que cuenten previamente con el estado DEVENGADO o PARCIAL emitido en 04.2.1.
RN-DEP-02 Precarga Inmutable de Datos Maestros La pantalla de validación precarga en modo solo lectura el número de oficio, la orden con firmas, el importe devengado y los órganos beneficiarios. El cajero tiene estrictamente prohibido alterar las partidas presupuestales de la solicitud.
RN-DEP-03 Validación de Techo contra Saldo Pendiente El monto del depósito capturado no puede superar bajo ninguna circunstancia el saldo pendiente por recaudar de la orden. En caso de discrepancia en exceso, debe canalizarse al catálogo 04.1.2 como aclaración.
RN-DEP-04 Unicidad del Folio Bancario El folio de operación bancaria o número de autorización emitido por la institución financiera (ej. BBVA Net Cash) es irrepetible para la misma cuenta recaudadora, blindando al sistema contra dobles aplicaciones.
RN-DEP-05 Obligatoriedad del Comprobante PDF Es mandatorio adjuntar el archivo PDF digitalizado del comprobante oficial de depósito o transferencia bancaria para poder habilitar el botón de confirmación de la recaudación.
RN-DEP-06 Afectación Forzosa del Momento Recaudado Al guardar la validación, el sistema transacciona en un solo bloque la amortización del saldo y detona la póliza contable de activo 1.1.1.2 Bancos / Tesorería vs 1.1.2.2 Cuentas por Cobrar y presupuestal 8.1.5 Recaudado.
