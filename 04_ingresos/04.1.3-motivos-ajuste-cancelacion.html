04.1.3

Motivos de ajuste o cancelación

Catálogo institucional de control y auditoría que estandariza las causas por las cuales se corrige, cancela, revierte o reclasifica una operación de ingreso, sustituyendo las notas de texto libre por tipificaciones trazables.

Pendiente de desarrollo Análisis funcional inicial (DOC-08) Responsable: Eunice
📌 Propuesta Institucional de Control y Auditoría

Este catálogo es una propuesta de control y trazabilidad del nuevo sistema SIAF-PJEV. No surge como una lista preexistente en manuales antiguos, sino como una solución a la debilidad de control interno que representaba permitir notas libres arbitrarias para anular o alterar cifras de recaudación.

Principio de Inmutabilidad: Ningún ajuste o cancelación elimina físicamente registros contables. Cada motivo seleccionado detona un contramovimiento auditable que queda asentado con usuario, fecha, hora y justificación técnica.

1 Descripción General

El catálogo 04.1.3 Motivos de ajuste o cancelación constituye la salvaguarda de gobernanza de datos en el subsistema de ingresos. Siempre que un analista o cajero requiera realizar una enmienda sobre un recibo de ingreso, un depósito aplicado o una distribución presupuestaria, el sistema le exigirá seleccionar obligatoriamente un motivo catalogado.

Cada motivo tipificado define el nivel de severidad de la enmienda (informativa, de control o crítica), determina si se requiere autorización jerárquica de la Jefatura de Tesorería o Contabilidad, y especifica si la corrección exige detonar una póliza contable de reverso o una reclasificación presupuestaria.

2 Objetivo y Alcance

Objetivo: Estandarizar y auditar las causales de modificación sobre los registros de ingresos, erradicando la discrecionalidad y asegurando que cada ajuste mantenga una explicación documental tipificada ante auditorías internas y externas (ORFIS).

Dentro del Alcance Fuera del Alcance
  • Padrón de 19 motivos iniciales de corrección, reverso y cancelación.
  • Clasificación por severidad: Informativa, De Control o Crítica.
  • Asociación con el Tipo de Movimiento específico (04.1.2) al que aplica.
  • Regla obligatoria de captura de justificación para motivos genéricos ("Otro").
  • Exigencia de visto bueno de rol superior en motivos críticos.
  • Preservación inalterable del historial de motivos utilizados.
  • Recepción física de acuerdos o escritos de inconformidad en papel.
  • Firmas electrónicas o cadenas criptográficas de validación.
  • Aprobaciones de reapertura mensual (gestionadas en 04.3.2).
  • Borrado de pólizas del libro diario.

6 Procedimientos Almacenados (Stored Procedures)

Gobernanza transaccional en PostgreSQL (esquema ingresos) bajo convención SECURITY DEFINER y respuesta JSONB { "error": 0, "mensaje": "OK", "data": [...] }.

6.1. Procedimiento LEER (ingresos.fn_leer_motivo_ajuste)

Parámetro (IN)TipoDescripción
p_usuarioVARCHAR(50)Usuario activo de sesión.
p_ejercicioINTEGEREjercicio fiscal en curso.
p_buscarVARCHAR(100)Texto libre para buscar por clave o nombre (opcional).
p_movimiento_aplicaVARCHAR(20)Filtro por tipo de movimiento que lo invoca (ej. CAN, AJU, RECLAS).
p_severidadVARCHAR(20)Filtro por nivel de severidad (INFORMATIVA, CONTROL, CRITICA).
p_motivo_idBIGINTID específico (NULL para listado completo).
p_estatusSMALLINT1 = Activos, 0 = Inactivos, NULL = Todos.
 
CREATE OR REPLACE FUNCTION ingresos.fn_leer_motivo_ajuste(
    p_usuario VARCHAR,
    p_ejercicio INTEGER,
    p_buscar VARCHAR DEFAULT NULL,
    p_movimiento_aplica VARCHAR DEFAULT NULL,
    p_severidad VARCHAR DEFAULT NULL,
    p_motivo_id BIGINT DEFAULT NULL,
    p_estatus SMALLINT DEFAULT 1
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ingresos, public
AS $$
DECLARE
    v_data JSONB;
BEGIN
    SELECT jsonb_agg(
        jsonb_build_object(
            'motivo_id', m.motivo_id,
            'clave', m.clave,
            'nombre', m.nombre,
            'descripcion', m.descripcion,
            'movimiento_aplica', m.movimiento_aplica,
            'requiere_observacion_adicional', m.requiere_observacion_adicional,
            'requiere_autorizacion', m.requiere_autorizacion,
            'rol_autorizador', m.rol_autorizador,
            'requiere_reverso_contable', m.requiere_reverso_contable,
            'requiere_reclasificacion', m.requiere_reclasificacion,
            'severidad', m.severidad,
            'permite_uso_periodo_cerrado', m.permite_uso_periodo_cerrado,
            'vigencia_inicio', m.vigencia_inicio,
            'vigencia_fin', m.vigencia_fin,
            'estatus', m.estatus,
            'total_usos', (
                SELECT COUNT(*) FROM ingresos.ingreso_ajuste a WHERE a.motivo_id = m.motivo_id
            )
        ) ORDER BY m.severidad DESC, m.clave
    ) INTO v_data
    FROM ingresos.motivo_ajuste_cancelacion m
    WHERE (p_motivo_id IS NULL OR m.motivo_id = p_motivo_id)
      AND (p_movimiento_aplica IS NULL OR m.movimiento_aplica = 'TODOS' OR m.movimiento_aplica ILIKE '%' || p_movimiento_aplica || '%')
      AND (p_severidad IS NULL OR m.severidad = p_severidad)
      AND (p_estatus IS NULL OR m.estatus = p_estatus)
      AND (p_buscar IS NULL OR m.clave ILIKE '%' || p_buscar || '%' OR m.nombre ILIKE '%' || p_buscar || '%');

    RETURN jsonb_build_object('error', 0, 'mensaje', 'OK', 'data', COALESCE(v_data, '[]'::jsonb));
EXCEPTION WHEN OTHERS THEN
    RETURN jsonb_build_object('error', -2, 'mensaje', SQLERRM, 'data', '[]'::jsonb);
END;
$$;

6.2. Procedimiento ABC (ingresos.fn_crud_motivo_ajuste)

Parámetro (IN)TipoDescripción
p_usuarioVARCHAR(50)Usuario que ejecuta la transacción.
p_ejercicioINTEGEREjercicio fiscal.
p_accionSMALLINT1 = Alta · 2 = Cambio · 3 = Baja lógica (Inactivar) · 4 = Reactivar.
p_motivo_idBIGINTNULL en Alta; ID existente en Cambio/Baja.
p_claveVARCHAR(20)Clave nemotécnica institucional (ej. MOT-REG-DUP).
p_datosJSONBPayload con nombre, severidad, reglas de autorización y flags.
 
CREATE OR REPLACE FUNCTION ingresos.fn_crud_motivo_ajuste(
    p_usuario VARCHAR,
    p_ejercicio INTEGER,
    p_accion SMALLINT,
    p_motivo_id BIGINT,
    p_clave VARCHAR,
    p_datos JSONB DEFAULT '{}'::jsonb
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ingresos, public
AS $$
DECLARE
    v_id BIGINT;
    v_count INT;
BEGIN
    -- 1 = ALTA
    IF p_accion = 1 THEN
        SELECT COUNT(*) INTO v_count FROM ingresos.motivo_ajuste_cancelacion WHERE clave = UPPER(TRIM(p_clave));
        IF v_count > 0 THEN
            RETURN jsonb_build_object('error', -1, 'mensaje', 'La clave de motivo ya existe.');
        END IF;

        INSERT INTO ingresos.motivo_ajuste_cancelacion (
            clave, nombre, descripcion, movimiento_aplica, requiere_observacion_adicional,
            requiere_autorizacion, rol_autorizador, requiere_reverso_contable,
            requiere_reclasificacion, severidad, permite_uso_periodo_cerrado,
            vigencia_inicio, vigencia_fin, estatus, observaciones, usuario_c, fecha_c
        ) VALUES (
            UPPER(TRIM(p_clave)),
            p_datos->>'nombre',
            p_datos->>'descripcion',
            COALESCE(p_datos->>'movimiento_aplica', 'TODOS'),
            COALESCE((p_datos->>'requiere_observacion_adicional')::BOOLEAN, false),
            COALESCE((p_datos->>'requiere_autorizacion')::BOOLEAN, false),
            p_datos->>'rol_autorizador',
            COALESCE((p_datos->>'requiere_reverso_contable')::BOOLEAN, false),
            COALESCE((p_datos->>'requiere_reclasificacion')::BOOLEAN, false),
            COALESCE(p_datos->>'severidad', 'CONTROL'),
            false,
            COALESCE((p_datos->>'vigencia_inicio')::DATE, CURRENT_DATE),
            (p_datos->>'vigencia_fin')::DATE,
            1, p_datos->>'observaciones', p_usuario, CURRENT_TIMESTAMP
        ) RETURNING motivo_id INTO v_id;

        RETURN jsonb_build_object('error', 0, 'mensaje', 'Motivo registrado exitosamente.', 'data', jsonb_build_object('motivo_id', v_id));

    -- 2 = CAMBIO
    ELSIF p_accion = 2 THEN
        UPDATE ingresos.motivo_ajuste_cancelacion SET
            nombre = COALESCE(p_datos->>'nombre', nombre),
            descripcion = COALESCE(p_datos->>'descripcion', descripcion),
            movimiento_aplica = COALESCE(p_datos->>'movimiento_aplica', movimiento_aplica),
            requiere_observacion_adicional = COALESCE((p_datos->>'requiere_observacion_adicional')::BOOLEAN, requiere_observacion_adicional),
            requiere_autorizacion = COALESCE((p_datos->>'requiere_autorizacion')::BOOLEAN, requiere_autorizacion),
            rol_autorizador = p_datos->>'rol_autorizador',
            requiere_reverso_contable = COALESCE((p_datos->>'requiere_reverso_contable')::BOOLEAN, requiere_reverso_contable),
            requiere_reclasificacion = COALESCE((p_datos->>'requiere_reclasificacion')::BOOLEAN, requiere_reclasificacion),
            severidad = COALESCE(p_datos->>'severidad', severidad),
            fecha_fin_vigencia = (p_datos->>'fecha_fin_vigencia')::DATE,
            observaciones = COALESCE(p_datos->>'observaciones', observaciones),
            usuario_m = p_usuario, fecha_m = CURRENT_TIMESTAMP
        WHERE motivo_id = p_motivo_id;

        RETURN jsonb_build_object('error', 0, 'mensaje', 'Motivo actualizado.', 'data', jsonb_build_object('motivo_id', p_motivo_id));

    -- 3 = BAJA LÓGICA (INACTIVAR)
    ELSIF p_accion = 3 THEN
        UPDATE ingresos.motivo_ajuste_cancelacion SET estatus = 0, usuario_m = p_usuario, fecha_m = CURRENT_TIMESTAMP
        WHERE motivo_id = p_motivo_id;

        RETURN jsonb_build_object('error', 0, 'mensaje', 'Motivo inactivado lógicamente.', 'data', jsonb_build_object('motivo_id', p_motivo_id));
    ELSE
        RETURN jsonb_build_object('error', -1, 'mensaje', 'Acción no soportada.');
    END IF;
EXCEPTION WHEN OTHERS THEN
    RETURN jsonb_build_object('error', -2, 'mensaje', SQLERRM);
END;
$$;

@ApiTags('04.1.3 Motivos de Ajuste o Cancelación')
@Controller('api/v1/ingresos/motivos-ajuste')
@UseGuards(JwtAuthGuard, RolesGuard)
export class MotivosAjusteController {
  constructor(private readonly motivosService: MotivosAjusteService) {}

8 Reglas de Negocio y Auditoría
RN-MOT-01 · Prohibición de Motivo Genérico Vacío

El sistema bloqueará el guardado si se selecciona el motivo MOT-OTR-AUT (Otro motivo autorizado) y el usuario deja vacío el campo de justificación adicional. Se exige un texto mínimo explicativo de al menos 20 caracteres.

RN-MOT-02 · Aprobación Obligatoria en Severidad Crítica

Todo ajuste o cancelación cuya causal sea calificada como Crítica entrará en estado Pendiente de Autorización y no tendrá efecto contable ni presupuestario hasta que el rol autorizador asiente su validación.

RN-MOT-03 · Preservación de Motivos Históricos Inactivos

Un motivo inactivado (estatus = 0) dejará de mostrarse en los selectores para nuevas operaciones, pero se conservará permanentemente visible en las consultas históricas de movimientos pasados.

RN-MOT-04 · Filtrado Contextual por Tipo de Movimiento

En las pantallas operativas de 04.2.1 y 04.3.1, el combo de motivos únicamente listará aquellos compatibles con el tipo de acción ejecutada (ej. en cancelación no se mostrarán motivos exclusivos de reclasificación).
